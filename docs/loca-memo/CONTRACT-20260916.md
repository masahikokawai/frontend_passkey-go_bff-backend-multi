## 2. 認証(OIDC BFFパターン)

- IdP: Keycloak (docker-compose、realm名 `training`, `--import-realm` で自動投入)
- ブラウザが持つのは BFF発行の HttpOnly/Secure/SameSite=Lax セッションCookie(`session_id`)のみ
  - JWTはブラウザに一切渡さない
- Redisキー:
  - `session:{sessionID}` → JSON `{user_id, access_token, refresh_token, id_token, access_token_exp, refresh_token_exp}` / TTL = refresh_token_exp に追従、リフレッシュ成功の都度再設定
  - `lock:session:{sessionID}` → SETNXによる分散ロック(TTL数秒)
  - 同一セッションへの同時リフレッシュ競合を防ぐ
- トークンリフレッシュ: リアクティブ方式
  - backendが401(access token expired)を返した時点でBFFがrefresh_tokenでリフレッシュし、成功なら元のリクエストを1回だけリトライ
  - 失敗ならRedisセッション削除+401返却
- ログアウト: RP-Initiated Logoutのみ
  - `POST /api/auth/logout` → Redis削除・Cookie削除 → Keycloakの`end_session_endpoint`へ`id_token_hint`付きで302
- CSRF: Double Submit Cookie方式
  - `csrf_token`(非HttpOnly)発行、Reactは状態変更系リクエストで`X-CSRF-Token`ヘッダに載せる
  - BFFミドルウェアで一致検証

## 3. BFFの公開API(BFF↔React契約)

| Method | Path | 説明 |
|---|---|---|
| GET | `/api/auth/login?redirect=<path>` | Keycloak Authorization Endpointへ302 |
| GET | `/api/auth/callback` | code受け取り→token交換→セッション発行→redirectへ302(実装は`FRONTEND_BASE_URL`(既定`http://localhost:5173`)+相対パスの絶対URLへリダイレクトする。相対パスのままだとbff自身のオリジンへの遷移になり404になるため。実機検証で判明) |
| POST | `/api/auth/logout` | セッション削除→Keycloak end_session へ302 |
| GET | `/api/me` | ログイン中: 200 `{ "user": {...}, "feature_flags": { "frontend.tasks-ts-rewrite": bool } }` / 未ログイン: 401 |
| GET | `/api/tasks` | 一覧。BFF内部で `bff.tasks-backend-v2` フラグを評価し backend v1(REST)/v2(gRPC)へルーティング |
| POST | `/api/tasks` | 作成 |
| GET | `/api/tasks/:id` | 詳細 |
| PATCH | `/api/tasks/:id` | 更新 |
| DELETE | `/api/tasks/:id` | 削除 |
| GET | `/api/labels` | ラベル一覧(v1のみ、gRPC化の対象外) |

React向けJSONのTask表現(v1/v2どちらを使っても同一形状にBFFが変換する):
```json
{
  "id": 1,
  "name": "string",
  "description": "string|null",
  "status": "waiting|work_in_progress|completed",
  "finishedOn": "2026-09-06",
  "labels": [{ "id": 1, "name": "string" }],
  "createdAt": "RFC3339",
  "updatedAt": "RFC3339"
}
```
一覧レスポンス: `{ "tasks": [...], "total": number, "limit": number, "offset": number }`
(v2 gRPCが内部でcursorページングを使っても、BFFがoffset/limit形式に変換してReactへ渡す
ただし v2経路は backend の ListTasksResponse に total件数が含まれないため、正確な総件数が分からない旨を示す `total: -1` を返す
Reactは現状totalを表示に使っていないため実害なし)

## 4. Feature Flag

- 実装: OpenFeature Go SDK + GO Feature Flag(ファイルベース `bff/internal/featureflag/flags.yaml`)
- フラグキー:
  - `frontend.tasks-ts-rewrite` (bool, default false) — React側Task一覧の新(TS)/旧(JS)コンポーネント切り替え
    - BFFが評価し`/api/me`経由でReactへ渡す
  - `bff.tasks-backend-v2` (bool, default false) — BFFがTask系リクエストをbackend v1(REST)/v2(gRPC)のどちらへルーティングするか
    - BFF内部でのみ評価、Reactには公開しない
- targeting keyは常にログイン中ユーザーの`user_id`(Keycloakの`sub`)を使う

## 5. backend(private network限定)

### v1 REST(意図的にN+1を再現する「旧実装」)
- `GET /internal/v1/tasks?user_id=&name=&status=&label_ids=&sort=&limit=&offset=`
- `POST /internal/v1/tasks`, `GET /internal/v1/tasks/:id`, `PATCH /internal/v1/tasks/:id`, `DELETE /internal/v1/tasks/:id`
- 実装方針: labelsをTaskごとにループで個別クエリ取得する(Preloadを使わない)
  - コメントで「これは学習用にN+1を再現した旧実装であり、本番のベストプラクティスではない」旨を明記

### v2 gRPC(Preload最適化・cursorページングの「新実装」)
- proto: `backend/proto/task/v1/task.proto`、サービス名 `TaskService`
- rpc: `ListTasks(cursor, limit) returns (tasks, next_cursor)`, `CreateTask`, `GetTask`, `UpdateTask`, `DeleteTask`
- cursorの実体は`uint64`(直前ページ最後のtask.ID、0=先頭/次ページ無し)
  - base64エンコード等の合成キーは使わない(実装がシンプルなためこの方式を採用)
  - id昇順固定で、finished_onソート等の併用はスコープ外
- 実装方針: `Preload("Labels")`でN+1を解消

### 認証
- JWT検証: 起動時にKeycloakのJWKS取得・メモリキャッシュ、`kid`不一致時のみ再取得
  - `iss`/`aud`/`exp`/`nbf`/`alg=RS256`を検証
- REST v1: Ginミドルウェア
  - gRPC v2: unary/stream interceptor
  - BFFからはAuthorizationヘッダ(v1)/metadata(v2)でaccess tokenを転送

## 10. Rails資産のうちKeycloak採用により置き換える範囲(重要な設計判断)

Rails版の `UserCredential`(bcryptパスワード)・`UserToken`(招待・パスワード設定用の32byteトークン、2日失効)は、
認証責務をKeycloakへ委譲したことで**そのまま移植しない**

理由と代替は以下の通り
- パスワード保存・検証・招待メール経由のパスワード設定フローは、Keycloak自体の管理コンソール/
  Required Actions(UPDATE_PASSWORD等)/ユーザー招待機能に置き換わる
  - 自前でパスワードを保持すると
  「認証情報の正本がKeycloakとRails由来DBの二重管理」になり、OIDC採用の目的(認証責務の一元化)に反する
- アプリ自身のDBには `users` テーブルのみ残し、認可・業務ロジックに必要な最小限の列
  (`id`, `keycloak_sub`, `name`, `email`, `role`, `created_at`, `updated_at`) を持つ
- プロビジョニング: BFFの `/api/auth/callback` 成功時、ID Tokenの`sub`/`name`/`email`クレームを使って
  backendへ「JIT(Just-In-Time)プロビジョニング」リクエストを送り、`keycloak_sub`で`users`をupsertする
  初回ログイン時に自動で行内が作成され、Railsにあった`resources :users`(サインアップ)は不要になる
- `role`(general/management)の初期値は`general`
  - 管理者への昇格はKeycloak側のrealm role
  - (`management`など)をID Tokenの`realm_access.roles`クレームに含め、JIT時に同期する
  - Admin::Usersのrole変更UIは残すが、変更内容はアプリDBの`role`列のみを更新し、Keycloak側realm role との同期は今回のスコープでは行わない(READMEに既知の制約として明記)
- 上記により `UserCredentialHandler` / `UserTokenHandler` / `UserMailer#password_set_mail` 相当は移植せず、README に「Keycloakが担うため意図的に対象外」と明記する

## 11. 外部公開API(BFF非経由、Client Credentials、Swagger UI)

BFFセッション認証とは別に、**サーバー間連携用の直接API**を追加する
これは「backendはBFF経由のみ公開」という原則の意図的な例外であり、この用途に限定してbackendを直接公開する

【セクション20.7で変更】公開ポート`:8081`は新設したgateway(`gateway/go`・`gateway/nginx`のいずれか)が
占有するようになり、backend自身の外部公開APIは内部アドレス`:8097`(`EXTERNAL_HTTP_ADDR`)へ変更した
外部から見た挙動(`:8081`・Client Credentials Grant・レスポンス形状)は変更前と同一

### 認証: Client Credentials Grant

- Keycloakに新クライアント `external-api-client` を追加(confidential、Service Accounts Enabled、Standard Flow/Direct Access Grants無効)
- トークン取得: `POST {keycloak}/realms/training/protocol/openid-connect/token` に `grant_type=client_credentials`
- backendは通常のBFF転送トークン検証(JWKSベース)を再利用しつつ、このルートに限り `azp`(authorized party)クレームが`external-api-client`であることを追加検証する専用ミドルウェア `RequireExternalClientAuth` を用意する
- 既知の制約としてREADMEに明記すること: `user_id`はクライアント側が任意に指定できるため、このクライアント資格情報を持つ者は任意ユーザーのタスクを読み取れる(サーバー間の信頼関係を前提にした設計であり、エンドユーザー単位の認可は行わない)

### エンドポイント

```
GET /external/v1/tasks?user_id={id}&page={n}&page_size={n}      # v1: offsetページング
GET /external/v1/tasks?user_id={id}&cursor={token}&limit={n}    # v2: cursorページング
```

- `user_id`: 必須
- v1(Feature Flag OFF, 既定): `page`既定1、`page_size`既定10
  - GORMの`Offset`/`Limit`
  - 深いページで劣化する弱点をコードコメントで明記
  - レスポンス: `{ "tasks": [...], "page": 1, "page_size": 10, "total": N }`
- v2(Feature Flag ON): `cursor`(省略時は先頭から)、`limit`既定10
  - `(created_at, id)`によるキーセット/cursorページング(`next_cursor`はbase64エンコードした`created_at`+`id`)
  - レスポンス: `{ "tasks": [...], "next_cursor": "string|null", "limit": 10 }`
- どちらもN+1回避のためPreloadを使う(N+1/Preloadの学習主題は既存のv1/v2と重複させず、ここではoffset/cursorページング性能の対比に絞る)

### Feature Flag

- `backend.external-tasks-pagination-v2` (bool, default false)
  - **backend自身が評価**する(このパスにBFFは介在しないため、flags.yamlはbackend側にも持つ)
  - targeting keyはAPIクライアントの`client_id`(トークンの`azp`)

### ネットワーク公開

- backendプロセス内に3つ目のリスナーを追加: 外部API専用Ginルーター `:8081`
  - 既存のREST v1(:8090)・gRPC v2(:9090)は`internal-net`限定のまま変更しない
  - (実機検証で判明: REST v1は当初:8080だったが、backend/bffをネイティブ実行する構成にした結果bffの既定ポート:8080と衝突するため:8090に変更した
  - README/docs/c4_container_v2.pumlの注記も参照)
- docker-composeで `:8081` のみ `127.0.0.1` 限定でホスト公開する

### Swagger UI

- `backend/openapi/external-api.yaml` (OpenAPI 3.0) を新規作成し、上記エンドポイントの両ページング方式を記述(実際の挙動はFeature Flagに依存する旨を明記)
- docker-composeに `swagger-ui` サービスを追加(`swaggerapi/swagger-ui`イメージ、`external-api.yaml`を読み取り専用マウント、`127.0.0.1`限定で公開)

## 13. Feature FlagのDB化とadmin UI(Go/Rails 2実装比較)

「実務ならadmin画面からクイックに切り替えられる方が良いのでは」という指摘を受け、Feature Flagの設定をファイル(flags.yaml)からMySQLへ移す
加えて、そのadmin CRUD画面を**Go+Gin実装とRails実装の2種類**で用意し、比較学習の題材にする(このプロジェクト全体の「同じ機能を複数の技術で書いて比較する」方針の延長)

### スキーマ(backendのgolang-migrateが正本として管理する
### admin/go・admin/rails は独自のマイグレーションを持たず、この既存テーブルへ接続するだけ)

```sql
CREATE TABLE feature_flags (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  flag_key VARCHAR(255) NOT NULL,
  description TEXT,
  default_variation VARCHAR(50) NOT NULL,   -- "on" | "off"
  enabled TINYINT(1) NOT NULL DEFAULT 1,     -- 0にするとGO Feature Flagの disable:true相当
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY index_feature_flags_on_flag_key (flag_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci;

CREATE TABLE feature_flag_audit_logs (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  feature_flag_id BIGINT UNSIGNED NOT NULL,
  flag_key VARCHAR(255) NOT NULL,             -- 非正規化(flag削除後も履歴として読めるように)
  before_default_variation VARCHAR(50),
  after_default_variation VARCHAR(50) NOT NULL,
  before_enabled TINYINT(1),
  after_enabled TINYINT(1) NOT NULL,
  changed_by VARCHAR(255) NOT NULL,           -- admin認証のユーザー名(Basic Auth、下記参照)
  changed_at DATETIME NOT NULL,
  PRIMARY KEY (id),
  KEY index_feature_flag_audit_logs_on_feature_flag_id (feature_flag_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci;
```

初期データ(既存3フラグ、既存flags.yamlの内容と一致させる):
`frontend.tasks-ts-rewrite` / `bff.tasks-backend-v2` / `backend.external-tasks-pagination-v2`
いずれも `default_variation="off"`, `enabled=1`

### backend側の変更

1. 上記2テーブルを追加するマイグレーション(`backend/migrations/000006_create_feature_flags.up.sql`等)+シード
2. `GET /internal/v1/feature-flags/export` — bffのGO Feature Flag HTTP retrieverがポーリングする
   エンドポイント
   `feature_flags`テーブルの内容をGO Feature Flagが期待するJSON形式
   (`{ "<flag_key>": { "variations": {"on":true,"off":false}, "defaultRule": {"variation": "<default_variation>"}, "disable": <!enabled> } }`)
   に変換して返す
   - 認証: ユーザーセッションに紐づかない定期ポーリングのため、通常のJWT(RequireAuth)は使えない
     共有シークレットヘッダ`X-Feature-Flag-Poll-Token`(環境変数`FEATURE_FLAG_POLL_TOKEN`で
     bff/backend双方に同じ値を設定)で認可する専用の軽量ミドルウェアを新設する
3. backend自身の外部API用フラグ評価(`backend.external-tasks-pagination-v2`)も、
   ファイル(`backend/internal/featureflag/flags.yaml`)からMySQL直読みの自作retrieverへ切り替える
   (backendは元々DBコネクションを持つため、HTTP経由にせず直接クエリしてよい)
4. admin CRUD相当の操作はbackendのHTTP APIとしては公開しない
   (admin/go・admin/railsがそれぞれ直接MySQLへ書き込む設計のため。理由は後述)

### bff側の変更

- GO Feature Flagの設定をFile retrieverからHTTP retriever(`${BACKEND_REST_BASE_URL}/internal/v1/feature-flags/export`、
  `X-Feature-Flag-Poll-Token`ヘッダ付き、`PollingInterval`は10秒程度)へ切り替える

## 16. ローカル(非Keycloak)認証の追加(3パターンのログインURL比較)

Keycloak(OIDC)のみだった認証方式に、比較学習用として「BFF自身がユーザー名/パスワードを検証し、自分でJWTを発行する」ローカル認証を追加する
Feature Flagによる切り替えは検討したが、ログイン前(セッション未確立)の分岐にFeature Flagは不向き、かつ実装コストの割に学習効果が薄いため不採用とし、**ログインURLを分ける**方式にした(2026-09-06確定)

### 16.1 ログインURLは3つ

| URL | 方式 | 発行するJWTの署名 |
|---|---|---|
| `GET /login` (frontend) → `POST /api/auth/login` (bff) | ローカル(既定) | HS256(共有シークレット) |
| `GET /login/rsa` (frontend) → `POST /api/auth/login/rsa` (bff) | ローカル | RS256(bffが自分の鍵ペアを保持、JWKSを公開) |
| `GET /login/keycloak` (frontend) → `GET /api/auth/login/keycloak` (bff、既存) | Keycloak OIDC | RS256(Keycloakの既存鍵、JWKS配布) |

既存の `GET /api/auth/login` (Keycloakへ302するもの)は `GET /api/auth/login/keycloak`にリネームする
frontendのトップのログイン画面には3つの入口(ローカルログインフォーム、「RSA版で試す」リンク、「Keycloakでログイン」ボタン)を並べる

### 16.2 スキーマ(usersから認証情報を分離)

Railsの元設計(`User` + `UserCredential`)に倣い、`users`テーブルには認証情報を持たせず、
別テーブルへ分離する(既存の`users.keycloak_sub`カラムは廃止し`user_keycloaks`へ移す)

```sql
-- 000008_split_user_credentials.up.sql
CREATE TABLE user_passwords (
  id                  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  user_id             BIGINT UNSIGNED NOT NULL,
  password_digest     VARCHAR(255) NOT NULL,
  password_expires_at DATETIME NOT NULL,
  created_at          DATETIME NOT NULL,
  updated_at          DATETIME NOT NULL,
  UNIQUE KEY idx_user_passwords_user_id (user_id),
  FOREIGN KEY (user_id) REFERENCES users(id)
);

CREATE TABLE user_keycloaks (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  user_id      BIGINT UNSIGNED NOT NULL,
  keycloak_sub VARCHAR(255) NOT NULL,
  created_at   DATETIME NOT NULL,
  updated_at   DATETIME NOT NULL,
  UNIQUE KEY idx_user_keycloaks_user_id (user_id),
  UNIQUE KEY idx_user_keycloaks_keycloak_sub (keycloak_sub),
  FOREIGN KEY (user_id) REFERENCES users(id)
);

-- 既存データ移行: users.keycloak_subが入っている行をuser_keycloaksへコピー
INSERT INTO user_keycloaks (user_id, keycloak_sub, created_at, updated_at)
SELECT id, keycloak_sub, NOW(), NOW() FROM users WHERE keycloak_sub IS NOT NULL AND keycloak_sub <> '';

ALTER TABLE users DROP COLUMN keycloak_sub;
```

`000009_seed_local_user.up.sql`で1人だけローカル認証用ユーザーをseedする
(登録画面は用意しない。実務でも社内管理者が最初の1人を手動発行するのは一般的なため)

- email: `local-user@example.com` / name: `ローカル太郎` / role: `general`
- `password_digest`: bcryptで`password`をハッシュ化した固定値
- `password_expires_at`: `2099-12-31 23:59:59`
  (期限切れ時の復旧手段(パスワード再設定画面等)を今回のスコープでは用意しないため、
  学習中に期限切れで詰まらないよう十分先の日付にする、という割り切り)

`model.User`から`KeycloakSub`フィールドを削除し、`model.UserPassword`/`model.UserKeycloak`を新設
`repository.User`の`GetByKeycloakSub`/`UpsertByKeycloakSub`は`repository.UserKeycloak`(新設)へ移す

### 16.3 パスワード検証は内部エンドポイント経由(bffはDBを直接見ない)

bffはDBに直接アクセスしない既存方針(CONTRACT.md冒頭)を維持する
パスワード照合はbackendの新しい内部エンドポイントで行う

```
POST /internal/v1/auth/verify-local-password
ヘッダ: X-Local-Auth-Internal-Token: <共有シークレット>(FEATURE_FLAG_POLL_TOKENと同じ
        考え方の別シークレット。まだJWTを持たない=RequireAuthが使えない呼び出しのため)
body:  {"email": "...", "password": "..."}
200:   {"user_id": 1, "name": "...", "email": "...", "roles": ["general"]}
401:   {"error": "invalid_credentials"}  -- email不一致 or bcrypt不一致
401:   {"error": "password_expired"}     -- 資格情報は正しいが有効期限切れ
```

bffはこのレスポンスを見て、`invalid_credentials`は「メールアドレスまたはパスワードが
正しくありません」、`password_expired`は「パスワードの有効期限が切れています」を
ログイン画面にエラー表示する(いずれもセッションは作らず、`/login`に留まる
「期限切れ→自動ログアウト」ではなく「そもそもログインさせない」という挙動)

### 16.4 bffがJWTを自分で発行する(HMAC/RSA)

`POST /api/auth/login`・`POST /api/auth/login/rsa`はどちらも上記の内部エンドポイントで
資格情報を検証した後、bff自身が新しいJWT(`sub`=内部user_id、`iss`=下記、`aud`="backend"、
`exp`=発行から24時間)を発行し、既存の`Session`(Redis)にそのJWTを`AccessToken`として
格納してセッションCookieを発行する(Keycloakログインと同じCookie/CSRF発行フローを再利用)

- ローカルセッションには`refresh_token`が存在しない
  - (有効期限24時間、更新なし)
  - ため、`Session`構造体に`AuthMode`(`"keycloak"`/`"local_hmac"`/`"local_rsa"`)フィールドを追加し、bff のリアクティブリフレッシュ処理(401受信時にrefresh_tokenで更新を試みる箇所)は`AuthMode != "keycloak"`の場合はリフレッシュを試みずセッションを破棄して401を返す
  - (frontendはこれを見て`/login`へ遷移する
  - 既存のKeycloakログイン時の401処理と分岐させる)
- `RefreshTokenExp`は`Store.save`のTTLガード(既存)をそのまま満たすため、ローカルセッションでは`AccessTokenExp`と同じ値を入れておく
  - (実際には参照されない)
- ログアウト時、`AuthMode == "keycloak"`の場合のみ既存のRP-Initiated Logout(`EndSessionURL`)を使う
  - ローカルセッションはRedis削除+Cookie削除のみで完了し、`redirectUrl`はfrontendのトップ(`/login`)を返す

発行するJWTの`iss`値:

| AuthMode | iss | 検証方法 |
|---|---|---|
| `local_hmac` | `bff-gin-local-hmac` | 共有シークレット(HS256)。`LOCAL_AUTH_HMAC_SECRET`をbff/backend両方に設定 |
| `local_rsa` | `bff-gin-local-rsa` | bffが起動時に生成するRSA鍵ペア。bffが`GET /.well-known/jwks.json`でJWKSを公開し、backendはKeycloak検証と同じ`authjwt.Verifier`(jwksURL/issuer/audienceの汎用実装)を1つ追加で持つだけで良い(新しい型は不要) |
| (既存) `keycloak` | Keycloakのissuer | 既存の`authjwt.Verifier` |

**RSA鍵はプロセスメモリ上でのみ生成・保持し、永続化しない**(bff再起動でRSAログインの既存セッションは検証不能になり、ユーザーは再ログインが必要になる
学習用途としての簡略化であり、本番であればJWKSのkid管理・鍵ローテーション・永続化が必要になる点を READMEに明記する)

### 16.5 backend側: 3方式のJWT検証をissuerで振り分け

`authjwt`パッケージに以下を追加する

- `HMACVerifier`(新設): `Verifier`と同じ`Verify(tokenString) (*Claims, error)`シグネチャを持つ、HS256版
  - `jwt.WithValidMethods([]string{"HS256"})`
- `Dispatcher`(新設): `map[string]TokenVerifier`(issuer文字列→verifier)を持ち、`jwt.ParseUnverified`で**署名検証前に**`iss`クレームだけを覗いてから対応する
  - verifierへ委譲する(委譲先が実際の署名検証を行う
  - 「振り分けのために覗く」ことと「検証を信頼する」ことは別、という2段階構造を維持する
  - 未知のissは即エラー)
- `RequireAuth`/`RequireExternalClientAuth`の引数型を`*Verifier`から
  `TokenVerifier`インターフェース(`Verify(string) (*Claims, error)`)に変更し、
  実運用では`*Dispatcher`を渡す

ユーザー解決(`resolveUserID`、v1/task.go・grpcserver/task_service.goの2箇所)は
`claims.Issuer`がKeycloakのissuerと一致する場合のみ`GetByKeycloakSub`、それ以外
(ローカル2方式)は`claims.Subject`を内部user_idとして`repository.User.Get(ctx, id)`で
直接引く(bffが発行するローカルJWTの`sub`は内部user_idそのものであるため)

### 16.6 frontend

`/login`(既定・ローカルフォーム)、`/login/rsa`(同フォーム、送信先のみ`/api/auth/login/rsa`)、
既存の「Keycloakでログイン」ボタンから`/api/auth/login/keycloak`への遷移、の3経路を
1つのログイン画面コンポーネントにまとめ、パスの違いで送信先を切り替える

### 16.7 この設計に至った経緯(学習メモ)

- 当初「フロントのログイン切り替えをFeature Flagで」という案を検討したが、
  ログイン前はセッションが無くuser_id単位のtargetingができないため不採用
- bffが自分の鍵ペアでJWKSを公開する(案B)は、一見「認可サーバーの自作」に見えるが、
  実際には「bffが自分自身のためだけに、1つの相手(backend)にだけ資格情報を証明する」
  という狭い用途であり、KubernetesのServiceAccount Tokenと同型のパターン
  避けるべきなのは「認可コードフロー・consent画面・複数クライアント対応」のような
  OAuth2の複雑なプロトコル部分の自作であって、署名・検証だけの単純な部分は
  既存ライブラリ(`golang-jwt/jwt`)+既存のJWKSキャッシュ実装の再利用で十分安全

## 17. Admin::Usersのユーザー管理(admin/go・admin/rails、backend経由)

参照元(`training`のRails、`training-go/gin`)には存在する`Admin::Users`のユーザー新規作成・削除機能が、
bff-ginには実装されていなかった(role変更のみ)
これは意図的な省略ではなく、CONTRACT.mdに理由の記載も無い未文書化の漏れと判明したため追加する(2026-09-07確定)

### 17.1 Feature Flagとは異なる設計にする理由

Feature Flag管理(セクション13)は admin/go・admin/railsから MySQL へ直接 GORM/ActiveRecord で接続する設計だった
しかしユーザー管理には`service/user.go`に既に業務ルール
(**最後の管理者をgeneralに降格できない**、`ErrLastManagerUser`)が実装されている
admin側がDBへ直接書き込む設計にすると、このルールをGo(admin/go)とRuby(admin/rails)の
両方で重複実装する必要があり、片方だけ実装漏れ・仕様のズレが起きるリスクがある

そのため**ユーザー管理だけは、admin/go・admin/railsからbackendの`/internal/v1/admin/users`系APIを
HTTP経由で叩く**設計にする(業務ルールはbackendの1箇所にだけ実装する)

### 17.2 「ユーザー追加」の対象はローカル認証ユーザーのみ

Keycloak経由のユーザーはJITプロビジョニング(セクション10)により初回ログイン時に自動作成される
既存の仕組みがあるため、admin画面での「事前作成」は不要(作っても未ログインなら`user_keycloaks`が紐付かず意味を持たない)
よって**admin画面で新規作成できるのはローカル認証ユーザーのみ**とする
作成時に name/email/初期パスワード/role を指定し、`users`+`user_passwords`の2テーブルへ同時に
INSERTする(セクション16.2のseedユーザーと同じ形
`password_expires_at`は作成時刻から100年後の固定値とし、運用上ほぼ無期限として扱う)

### 17.3 backend側API(新規、共有シークレットで認可)

`/internal/v1/users`(既存、RequireAuth配下、実際には現状どこからも呼ばれていない死んだルート)とは別に、admin専用のルートグループを新設する
認可方式はセクション13の`X-Feature-Flag-Poll-Token`・セクション16.3の`X-Local-Auth-Internal-Token`と同じ「共有シークレットヘッダ」パターン

```
新規ミドルウェア: RequireAdminInternalToken(ヘッダ X-Admin-Internal-Token)
新規config: ADMIN_INTERNAL_TOKEN(backend/admin/go/admin/rails共通の既定値、開発用固定文字列)

GET    /internal/v1/admin/users        一覧。既存のUserService.Listを再利用
POST   /internal/v1/admin/users        新規作成(ローカル認証ユーザーのみ)
  body: {"name","email","password","role"}
  201: {"user_id","name","email","role"}
  422: email重複、password空、role不正 等
PATCH  /internal/v1/admin/users/:id/role  role変更。既存のUserService.UpdateRoleを再利用
  422: ErrLastManagerUser(最後の管理者を降格しようとした。既存のrenderServiceErrorのマッピングをUpdateRoleと共有)
DELETE /internal/v1/admin/users/:id    削除
  204: 成功。トランザクションで user_passwords → user_keycloaks → tasks(task_labelsごと) → users の順に削除
  422: ErrLastManagerUser(最後の管理者を削除しようとした。同上)
  404: 対象が存在しない
```

`UserService`に`Create`・`Delete`を追加し、`Delete`は`UpdateRole`と同じ
「対象がmanagementかつ現在のmanagement人数が1人以下なら拒否」ロジックを共有する

### 17.4 admin/go・admin/railsの画面

Feature Flag管理画面と同じBasic Auth配下に、`/users`(一覧+作成フォーム+role変更+削除ボタン)を追加する
Bootstrap 4.3.1で既存のFeature Flag画面と統一感のあるデザインにする
admin/go・admin/railsとも、上記backend APIを叩くだけのシンプルなHTTPクライアントとして実装し、
バリデーションエラー・最後の管理者ガードのエラーはbackendからのレスポンスをそのまま画面に表示する

新規環境変数: admin/go `ADMIN_INTERNAL_TOKEN`・`BACKEND_INTERNAL_BASE_URL`(既定`http://localhost:8090`)、admin/rails 同様(Rails流の命名で)

### 18.3 環境変数

### 18.5 フレームワークごとに「できないこと」一覧

6フレームワークは基本的に同じシナリオを実装できるが、
いくつかは特定のフレームワークで実現不可能、または回避策が必要だった
個別のREADMEにも記載しているが、横断的に一覧できるようここにまとめる

| フレームワーク | できないこと・制約 | 対応 |
|---|---|---|
| **Cypress** | WebAuthnの仮想認証器(Virtual Authenticator)を操作する第一級APIが無い | パスキー登録/ログインのe2eシナリオ、および「パスキー登録がパスワードログインを壊さない回帰確認」シナリオ(パスキー登録が前提のため同じ理由で不可)は実装を見送り(`e2e/cypress/README.md`に理由を明記) |

| **go-rod** | 自動ダウンロードされる既定のChromium(128.0.6568.0)が`PublicKeyCredential.parseCreationOptionsFromJSON`/`parseRequestOptionsFromJSON`を実装していない | このシナリオに限り`CHROME_BIN`環境変数で実機のGoogle Chromeを起動するよう回避(他のシナリオは既定のChromiumのまま。恒久的な制約ではなくブラウザバージョン依存の問題) |

| Playwright(JS)・Selenium・chromedp・playwright-go | 上記以外で現時点で判明している制約なし | - |

Virtual Authenticator機能・Network/Fetchドメインでのリクエスト制御・複数タブ操作等、
いずれも(Cypressの2点・go-rodの1点を除き)何らかの形で実現できている

## 19. Task登録UXの3パターン比較(多値Feature Flag、`frontend.task-create-ux`)

Task登録フォームが`/tasks`画面上部に常設されている現行UIについて、実務でのUI/UX観点の議論を経て、
「一覧上部の常設フォーム」「モーダル」「別ページ遷移」の3パターンを比較学習用に追加実装する

### 19.1 なぜ多値(multivariate)フラグにするのか

既存3フラグ(`frontend.tasks-ts-rewrite`等)はいずれも「新/旧」の2択(boolean)だが、今回は
「3つの排他的なUXパターンから1つを選ぶ」ため、独立したbooleanフラグを3つ用意する設計は避ける
N個のbooleanフラグで排他的な状態を表現すると、複数が同時にONになる無効な組み合わせを
アプリ側で防ぐ責任を負うことになる(Feature Flagのアンチパターンとして広く知られている)
かわりに**1つのフラグに3つの値**を持たせる

```
frontend.task-create-ux
  variations: {"inline": "inline", "modal": "modal", "page": "page"}
  default_variation: "inline"
```

### 19.2 スキーマ変更(既存3フラグの挙動は一切変えない)

`feature_flags`テーブルに`variations`(JSON型)カラムを追加する新規マイグレーション

```sql
ALTER TABLE feature_flags ADD COLUMN variations JSON NULL AFTER default_variation;

UPDATE feature_flags SET variations = JSON_OBJECT('on', true, 'off', false)
WHERE flag_key IN ('frontend.tasks-ts-rewrite', 'bff.tasks-backend-v2', 'backend.external-tasks-pagination-v2');

INSERT INTO feature_flags (flag_key, description, default_variation, enabled, variations, created_at, updated_at)
VALUES ('frontend.task-create-ux', 'Task登録UIの3パターン(inline/modal/page)を切り替えるRelease Toggle', 'inline', 1,
  JSON_OBJECT('inline', 'inline', 'modal', 'modal', 'page', 'page'), NOW(), NOW());
```

既存3フラグは`variations`列の中身が`{"on":true,"off":false}`になるだけで、これは
`BuildFlagConfigJSON`(セクション13)が従来ハードコードしていた値と完全に同一

そのため既存3フラグの評価結果・JSON出力は一切変わらない(後方互換)

### 19.3 backend側の変更

`BuildFlagConfigJSON`(`backend/internal/featureflag/mysql_retriever.go`)を、`variations`列を
そのまま読んで出力するよう一般化する(ハードコードされた`map[string]bool{"on":true,"off":false}`を撤廃)

`model.FeatureFlag`に`Variations string`(JSON生文字列)フィールドを追加

### 19.4 bff側の変更

`Evaluator`(`bff/internal/featureflag/evaluator.go`)に、既存の`BoolValue`とは別に
`StringValue(ctx, flagKey, defaultValue string, userID string) string`を新設
(OpenFeature Go SDKは`StringValue`を標準サポートしている)

`auth.Handler.Me()`が`GET /api/me`のレスポンスに
`frontend.task-create-ux`の評価結果(文字列)も含めるようにする(既存の`frontend.tasks-ts-rewrite`
と同じ扱い)

### 19.5 frontend側の変更

`features/tasks/`に3パターンを実装する

- **inline**(既存): `TaskList.tsx`のまま(変更不要)
- **modal**: 一覧に「タスクを登録」ボタンを新設
  - クリックでモーダル(既存`TaskForm.tsx`を流用)を開く
  - 別ルートには遷移しない
- **page**: 一覧に「タスクを登録」リンクを新設
  - クリックで別ルート(`/tasks/new`)へ遷移し、専用ページで`TaskForm.tsx`を表示
  - 保存/キャンセルで`/tasks`へ戻る(戻る導線を必ず用意する
  - セクション「戻る導線」の教訓を踏まえる)

`TaskListSwitch.tsx`と同じ考え方で、`frontend.task-create-ux`の値に応じて表示を切り替える
コンポーネントを新設する(3値なのでswitch文になる)

### 19.6 admin/go・admin/railsの変更

編集画面を、`variations`の中身に応じて汎用的に描画するよう変更する

- 値が2つかつ`{on: true, off: false}`の場合(既存3フラグ) → 既存のON/OFFトグルUIのまま(画面・挙動とも無変更)
- それ以外(今回の3値フラグ等) → variationsのキー一覧から選ぶselect/radioを動的に描画

これにより既存3フラグの管理画面は今まで通り、新フラグは汎用ロジックで自動的に描画される
(このフラグ専用のハードコードされた画面は作らない)

## 19.7 legacy(JavaScript)側にも3UXパターンを実装(直交する2軸の完全な組み合わせ)

セクション19の初回実装では、`frontend.task-create-ux`をTypeScript実装側にのみ適用し、
`legacy/TaskList.jsx`は常にinlineのままという簡略化をしていた

ユーザーからの明示的な要望により、「TS/JS」×「inline/modal/page」の2軸を完全に独立・組み合わせ可能にする

- `legacy/`配下
  - 既存の`TaskListModal.tsx`・`TaskListPage.tsx`・`TaskFormPage.tsx`・`TaskCreateUXSwitch.tsx`と対になるJavaScript版を新設する
  - (`legacy/TaskListModal.jsx`等)
  - ロジックは`legacy/TaskList.jsx`の既存CRUD処理(`handleSubmit`/`handleDelete`等)を再利用し、
  - TypeScript版の構成(モーダルのBootstrapマークアップ、別ページの「一覧へ戻る」導線)をそのまま踏襲する
- `TaskListSwitch.tsx`(`frontend.tasks-ts-rewrite`の切り替え元)は、falseの場合に
  `TaskListLegacy`(常にinline)ではなく、legacy版の`TaskCreateUXSwitch`(3UX切り替え対応)を描画するよう変更する
- `app/routes.tsx`の`/tasks/new`・`/tasks/:id/edit`ルートは、現状TypeScript版の`TaskFormPage`を
  決め打ちしているが、`frontend.tasks-ts-rewrite`の値に応じてTS版/JS版のフォームページを
  切り替える必要がある(新しいスイッチコンポーネントを1つ挟む形になる見込み)

## 20. backend多言語実装比較(Go/Rust/Scala×2/Rails)とプロトコル(REST/gRPC)の直交2軸、外部公開APIゲートウェイ新設

Task CRUD(内部)と外部公開APIの実処理を、Go以外の言語・フレームワークでも比較実装する

既存の「bffはbackend経由でのみデータを扱う」原則は維持したまま、
「backendの中身がどの言語で動いているか」をFeature Flagで切り替えられるようにする

### 20.1 対象範囲

- **対象**: Task CRUD(内部、bff経由)+ 外部公開API(bff非経由、直接)
- **対象外**: Label CRUD・Admin::Usersの内部API・Feature Flag管理APIは、これまで通りGoのみ
  (既存の`backend/`実装のまま変更しない)

### 20.2 Feature Flag設計(直交する2軸、それぞれ独立したフラグ)

言語の選択とプロトコルの選択は互いに独立した軸(どの言語でもREST/gRPCどちらも成立する)なので、
セクション19.1の原則(独立した軸は別フラグ、1つの排他選択は1つのフラグにまとめる)通り2フラグに分ける

```
backend.task-language (多値、5値)
  variations: {"go":"go", "rust":"rust", "scala-http4s":"scala-http4s",
               "scala-pekko":"scala-pekko", "rails":"rails"}
  default_variation: "go"

backend.task-protocol (多値、2値。既存bool "bff.tasks-backend-v2" を汎化)
  variations: {"rest":"rest", "grpc":"grpc"}
  default_variation: "rest"
```

`backend.task-protocol`は既存の`bff.tasks-backend-v2`(bool)を置き換える形になるため、
移行時は`bff.tasks-backend-v2=false→"rest"`, `true→"grpc"`に対応させ、
既存フラグの`variations`列(`{"on":true,"off":false}`)はそのまま残して後方互換を保つ
(`bff.tasks-backend-v2`自体は非推奨として残置し、新規に`backend.task-protocol`を追加するマイグレーション)

`backend.task-language`は**内部CRUD(bff経由)と外部公開API(ゲートウェイ経由)の両方で同一の値を共有**する

内部と外部で答える言語がズレる(内部はGo、外部はRustのように)不整合を避けるため

一方`backend.task-protocol`は内部CRUDのみが対象(外部公開APIは常にRESTとして公開するため無関係)

→ 内部CRUD: 5言語 × 2プロトコル = 10パターン。外部公開API: 5言語(常にREST) = 5パターン

### 20.3 ディレクトリ構成(既存`backend/`はGoのまま変更しない)

```
backend/                  # 既存Go実装、変更なし(セクション5・7)
backend-rust/             # 新規、Rust実装
backend-scala-http4s/     # 新規、Scala(http4s)実装
backend-scala-pekko/      # 新規、Scala(Pekko HTTP)実装
backend-rails/            # 新規、Rails実装(admin/railsとは別物、backendの役割を担う)
gateway/                  # 新規、外部公開API用ゲートウェイ(20.8)
  go/                     # Go製リバースプロキシ実装
  nginx/                  # nginx設定 + flagポーリング用サイドカースクリプト
```

`e2e/playwright`・`e2e/cypress`…と同じく「並列ディレクトリ」パターンを踏襲し、
既存`backend/`のGoモジュールパス(bffからのimport含む)には一切影響を与えない

### 20.4 各言語・フレームワークの技術選定

| 言語 | REST | gRPC | 備考 |
|---|---|---|---|
| Go(既存) | Gin | 標準gRPC | セクション5のまま |
| Rust | Axum | tonic | tokio/hyper/tonicと同じTokioチーム製、towerを共有基盤とするためAxum+tonicが最も自然な組み合わせ |
| Scala(http4s) | http4s | fs2-grpc | cats-effect系のTypelevelエコシステム。ライセンス懸念なし |
| Scala(Pekko) | Pekko HTTP | pekko-grpc | **Akka HTTP(BSL、商用ライセンス)ではなくApache 2.0継続フォークのPekko HTTPを採用**。学習用OSSプロジェクトとしてライセンスリスクを避けるため |
| Rails | ActionController | `grpc` gem(公式Ruby gRPC実装、C拡張ベース) | 既存`admin/rails`(Feature Flag/ユーザー管理のadmin画面)とは別コンポーネント |

### 20.5 ワイヤー契約パリティの原則(最重要)

5言語すべての実装は、REST APIのパス・JSONレスポンス形状・ステータスコード・エラーボディ
(`{"error":"user_not_provisioned"}`等、セクション17参照)、およびgRPCの`.proto`定義・
`codes.PermissionDenied`等のステータスコード・エラーメッセージ文字列を、
既存Go実装(v1 REST・v2 gRPC)と完全に一致させる

この原則により、bff側・ゲートウェイ側は「どの言語が応答したか」を意識する必要が一切なくなり、
新しいクライアントコードを言語ごとに書く必要がない(20.6参照)
各言語実装の README に「意図的にGo実装と同一のワイヤー契約に合わせている」旨を明記すること

### 20.6 bff側の変更(最小限で済む理由)

`bff/internal/proxy/task_route.go`の`TaskBackendClient`は既にインターフェースであり、既存の`V1`(REST)・`V2`(gRPC)はそのインスタンスに過ぎない
両者ともbase URL/addrを外部設定(`BACKEND_REST_BASE_URL`・`BACKEND_GRPC_ADDR`)から受け取る設計のため、
20.5のワイヤー契約パリティが保たれる限り、**新しいクライアント実装コードは不要**で、
同じ構造体を言語ごとに異なるURL/addrでインスタンス化するだけで済む

- `config.go`: env変数を2個→10個に拡張(例: `BACKEND_GO_REST_BASE_URL`, `BACKEND_RUST_GRPC_ADDR`等、
  `{言語}_{プロトコル}`の組み合わせ)
- `TaskRoutes`: `V1`/`V2`フィールドを`Clients map[string]TaskBackendClient`
  (キーは`"go:rest"`等、`backend.task-language:backend.task-protocol`の組み合わせ)に変更
- `pickClient`:
  - 2つのフラグ(`backend.task-language`の`StringValue`・`backend.task-protocol`の`StringValue`)を評価し、
  - 組み合わせキーで`Clients`を引く形に変更
  - ログ出力は既存の「振り分け結果を必ず記録する」方針を維持
- `do()`のエラー分類(`classifyStatus`/`classifyGRPCErr`)は変更不要(20.5のパリティが前提)

### 20.7 外部公開APIゲートウェイ(新設)

現状「外部公開APIはbffを経由しない」設計のため、`backend.task-language`を評価して
リクエストを適切な言語のbackendへ振り分ける主体が存在しない

この役割を担う**ゲートウェイ**を`:8081`(既存の外部公開APIのポート)に新設し、実際の5言語backendは別ポートへ配置し直す

- ゲートウェイは`backend.task-language`(bffと同じ評価ロジック・ポーリング間隔、backendの
  `GET /internal/v1/feature-flags/export`を同じ共有トークンで直接ポーリングする。admin/go・
  admin/railsのようにMySQLへ直接繋ぐ第三の経路は増やさない)を評価し、対応する言語の
  外部公開APIへリバースプロキシする(常にRESTのみ、外部公開APIはプロトコル軸を持たない)
- swagger-uiのServer URLは`:8081`のまま変更不要(ゲートウェイが透過的に振り分けるため)
- 全言語が20.5のワイヤー契約パリティを満たす前提なので、OpenAPI仕様(swagger-ui)は1つのまま
  全言語実装に対して有効

5言語すべてが`/external/v1/tasks`(offset/cursor両ページング、Client Credentials
Grant認証)を実装済み(ポートはGo`:8097`・Rust`:8098`・Scala(http4s)`:8099`・Scala(Pekko)`:8100`・
Rails`:8101`)

ページネーション方式の切り替えflag(`backend.external-tasks-pagination-v2`)は
5言語で共有する1つのflagとして扱う(ユーザーの明示的な指示)

ゲートウェイ(Go製・nginx製とも)は
実機で`backend.task-language`の5値全てが実際にフォールバック無しでそれぞれの言語へ
ルーティングされることを確認済み

### 20.8 ゲートウェイ実装自体の選択(Go製 / nginx製、インフラ学習用)

ゲートウェイの実装そのものも2種類用意し比較する

- **Go製**: アプリケーションコード内でflagをポーリングし、都度ルーティング先を決定する(bffの`pickClient`と同じ設計思想)
- **nginx製**: nginx自体はflag評価ロジックを持てないため、外部のサイドカースクリプトが
  `backend.task-language`を定期ポーリングし、`upstream`定義ファイルを書き換えて`nginx -s reload`をトリガーする
  (実務でよくある「設定ファイル生成+リロード」方式)

**この2実装の切り替えはDBのfeature flagとは別軸**として扱う
ゲートウェイはリクエストの受け口
そのものであり、どちらのプロセスがポートをbindするかを実行時にflagで切り替えることはできない
(off側のプロセスはリクエストを受け取れないため、flag評価の機会がない)

そのため**デプロイ時(起動するコマンドの選択)による切替**とする

gateway自体はbackend/bff/frontendと
同様docker-composeに加えずネイティブ実行する(`cd gateway/go && go run .` または
`cd gateway/nginx && ./start.sh`のいずれか一方のみを起動する。どちらも`:8081`をbindするため同時起動は不可)

### 20.9 実装順序(規模が大きいため段階的に進める)

   ―当初「2プロセス」と記載していたが、外部公開API(`config/puma_external.rb`)もREST(`config/puma.rb`)とは

### 20.10 実機検証で判明した既知の制約への対応: 5言語×3種類(REST/外部公開API/gRPC)全てにリクエスト単位のログを追加(2026-09-11)

**発端**: ユーザーによる手動検証(ランブックのbackend多言語比較セクション)で、Rust・Scala(http4s)・
Scala(Pekko)の3言語には起動時のポートbindログしか無く、**実際にどのリクエストを処理したか
ログから一切確認できない**ことが判明した。ユーザーから「実務のRust開発でログが出ないのは

## 22. パスキー(WebAuthn)の追加

既存ユーザー(Keycloak発行・ローカル認証のいずれか)向けの**追加の認証手段**として、パスキー
(WebAuthn discoverable credential、いわゆる「usernameless」ログイン)を追加する

### 22.1 スコープ・対象範囲

- 対象: **bffのローカル認証(HMAC/RSA)ユーザーのみ**
  - Keycloak発行ユーザー向けのパスキー
  - (Keycloak自体のWebAuthn認証フロー設定)は、既存の全Keycloakログインフロー
  - (既存frontend+bffの「Keycloakでログイン」ボタンも含む)に影響する範囲の広い変更になるため、
  - **今回は対象外**とする(ユーザーの明示的な判断)
- `frontend-rails`(without-bff・with-bffいずれも)も対象外(常にKeycloak経由のため)
- 既存ユーザーへの**追加**の認証手段であり、パスキーからの新規サインアップは対象外
  (ユーザー作成は引き続きadmin経由またはKeycloak JITプロビジョニングのみ)

**【2026-09-11追記、ユーザーの明示的な指示によりスコープ拡張】** `frontend-rails/without-bff`は
上記の「対象外」から外し、**追加でパスキー機能の対象とする**(詳細設計は22.9参照)。
ただし「Keycloak自体のWebAuthn認証フロー設定」を触るわけではなく、既存の設計(go-webauthn/
`webauthn` gemによるアプリケーション層でのWebAuthn実装、backendの`webauthn_credentials`
テーブルを共有)をそのまま踏襲する。React `frontend`+`bff`の「Keycloakでログイン」ボタン自体には
一切手を入れない(そちらは引き続き対象外のまま)。

### 22.2 技術選定

- bff: `github.com/go-webauthn/webauthn`(W3C仕様準拠のGoライブラリ)
- frontend: ブラウザ標準の`navigator.credentials.create()`/`.get()`を直接呼ぶ(追加ライブラリ不要)
- **discoverable credential(resident key)方式を採用**する
  - ログイン画面で個別にメールアドレス等を入力せず、「パスキーでログイン」ボタン
  - → `navigator.credentials.get()`(allowCredentials指定無し)
  - →ブラウザ/OSが利用可能なパスキーを提示、という流れにする
- クロスデバイス認証(QRコード表示→スマホでスキャン→スマホ側で生体認証→PC側ブラウザへ結果が戻る)
  - ブラウザ/OSの標準機能(WebAuthnのhybrid transport)であり、こちら側での実装は不要
  - (`navigator.credentials.get()`を正しく呼ぶだけで、ブラウザが自動的にこの導線を提供する)

### 22.3 スキーマ(backendのgolang-migrateが正本)

```sql
CREATE TABLE webauthn_credentials (
    id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id       BIGINT UNSIGNED NOT NULL,
    credential_id VARBINARY(1024) NOT NULL,  -- base64urlデコード後の生バイト列
    public_key    BLOB            NOT NULL,  -- COSE形式の公開鍵
    sign_count    BIGINT UNSIGNED NOT NULL DEFAULT 0,
    transports    VARCHAR(255)    NULL,      -- "internal,hybrid" 等、カンマ区切り
    name          VARCHAR(255)    NULL,      -- ユーザーが付ける端末名(任意)
    created_at    DATETIME        NOT NULL,
    updated_at    DATETIME        NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY index_webauthn_credentials_on_credential_id (credential_id),
    KEY index_webauthn_credentials_on_user_id (user_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci;
```

`credential_id`をグローバルに一意なルックアップキーにする(discoverable credentialのログイン時、
ユーザーを未特定の状態で「このcredential_idは誰のものか」を引く必要があるため)

### 22.4 backend: 新規内部API

| エンドポイント | 認証 | 用途 |
|---|---|---|
| `POST /internal/v1/auth/webauthn/credentials` | 通常の`RequireAuth`(JWT) | ログイン中ユーザーが新しいパスキーを登録(bffが検証済みのattestationから抽出した公開鍵等を保存) |
| `GET /internal/v1/auth/webauthn/credentials/:credential_id` | 共有シークレットヘッダ(`RequireWebauthnInternalToken`、`WEBAUTHN_INTERNAL_TOKEN`環境変数。ログイン試行中でJWTを持たないため、`RequireLocalAuthInternalToken`と同じ方式) | ログイン時、bffがcredential_idからuser_id・公開鍵・sign_countを引く |
| `PATCH /internal/v1/auth/webauthn/credentials/:credential_id/sign-count` | 同上(共有シークレット) | ログイン成功後、リプレイ攻撃対策のsign_countを更新 |

### 22.5 bff: 新規ルート

当初`/api/auth/webauthn/*`という命名で設計・実装したが、
「webauthnという技術用語だと何を登録するエンドポイントか分かりにくい」というユーザーからの
明示的な指摘を受け、パスに`passkey`という語を含める命名へ統一した(bff-rails新設時に
命名規則を揃える必要が生じたのが直接のきっかけ)
**bff内部の型名・メソッド名(`WebauthnRegisterBegin`等、go-webauthnライブラリを指す)はそのままで、HTTPパスのみ変更している**

| エンドポイント | 認証 | 用途 |
|---|---|---|
| `POST /api/auth/passkey/register/begin` | 要ログイン | 登録用challenge生成(go-webauthnの`BeginRegistration`)、Redisに一時保存 |
| `POST /api/auth/passkey/register/finish` | 要ログイン | attestation検証(`FinishRegistration`)→backendへ`POST .../credentials`で永続化 |
| `POST /api/auth/passkey/login/begin` | 不要(未ログイン) | discoverable credential用のassertion challenge生成(`allowCredentials`指定無し) |
| `POST /api/auth/passkey/login/finish` | 不要(未ログイン) | assertion検証。返ってきた`credential_id`でbackendへ`GET .../credentials/:id`を呼びuser_id/公開鍵/name/email/rolesを取得(bffがそのままセッションを発行するため、backend側もこの3項目を追加で返すよう拡張した)→署名検証→sign_count更新→セッション発行(`auth_mode=passkey`、既存のHMAC/RSA/Keycloakと同じセッション発行経路に合流) |

### 22.8 実機バグ: クラウド同期パスキーでログインが常に失敗する(Backup Eligible flag inconsistency)

**症状**: パスキー登録は成功するが、登録直後にログアウトして同じパスキーでログインすると
`login/finish`が401になり、「パスキーでのログインに失敗しました」となって常に失敗する。
Chrome(CDP仮想認証器)を使ったe2eテスト(`webauthn_e2e_test.go`、6フレームワークのe2e)は
全てpassし続けており、自動テストでは一切検知できなかった。

**原因**: WebAuthnのauthenticator dataには、その認証器がクラウド同期対応か(Backup Eligible=BE)、
実際に同期済みか(Backup State=BS)を示すフラグがある。`go-webauthn`(v0.18.0)は、
登録時に記録したBE/BSフラグとログイン時にassertionで申告されたBE/BSフラグが一致することを検証し、
不一致なら`protocol.Error{Type:"invalid_request", Details:"Backup Eligible flag inconsistency
detected during login validation"}`で拒否する。

bffは元々BE/BSフラグを一切保存しておらず(backendの`webauthn_credentials`テーブルにカラム自体が
無かった)、ログイン検証時に`webauthn.Credential`を再構築する際`Flags`フィールドを未設定
(ゼロ値=false/false)のまま`go-webauthn`に渡していた。

Google パスワードマネージャー・iCloudキーチェーン・Windows Hello(クラウド同期あり)など、
実際のパスキーはほぼ全て`BackupEligible=true`を申告するため、上記の不一致が必ず発生し、
実機では**登録の成否に関わらずどのパスキーログインも100%失敗する**状態だった。
一方、e2eテストで使う`github.com/descope/virtualwebauthn`(chromedp/go-rod等)やCDP仮想認証器は
デフォルトで`BackupEligible=false`を返すため、登録時・ログイン時の両方でfalse同士が一致してしまい、
この不具合を一切検知できなかった。

**診断の経緯**: (1) e2eテストは再現せずpass → 基本経路の破壊ではないと判断、
(2) bffのルート定義・RP ID(`localhost:5173`、`127.0.0.1`ではないことをユーザーに確認)を確認して除外、
(3) `WebauthnLoginFinish`のエラーハンドリングが`go-webauthn`が返す`protocol.Error`の`Type`/`Details`/
`DevInfo`を握りつぶしログに出力していなかったため、`bff/internal/auth/webauthn.go`に診断ログを追加、
(4) ユーザーの実ブラウザでの再現テストでこのログから実際のエラー文言が判明、
(5) `go-webauthn`のソース(`webauthn.CredentialFlags`)を確認し根本原因を特定。

**修正**:
- `backend`: migration `000015_add_webauthn_credential_flags`で`webauthn_credentials`に
  `backup_eligible`/`backup_state`(TINYINT(1))を追加。モデル・service・handler
  (登録時の保存・`GET .../credentials/:id`のレスポンス)を拡張。
- `bff`: `WebauthnCredentialStore`インターフェースの`Register`/`Lookup`シグネチャに
  `backupEligible, backupState bool`を追加。`WebauthnRegisterFinish`は
  `credential.Flags.BackupEligible/BackupState`(go-webauthnが登録時のattestationから
  実際に解析した値)をbackendへ送信。`WebauthnLoginFinish`の discoverable-user
  ハンドラは、backendからLookupした値で`webauthn.Credential`の`Flags`フィールドを
  正しく復元してから検証に渡すよう修正。
- `bff/internal/auth/handler.go`: `Handler`に`*slog.Logger`を追加し、以後
  `go-webauthn`の`protocol.Error`(Type/Details/DevInfo)を握りつぶさずログ出力するようにした
  (次回同種の不具合が起きた際、実機を借りずログだけで原因特定できるようにするため)。
- 回帰テスト: `webauthn_e2e_test.go`で登録時のBE/BSフラグをログイン時のLookupスタブにも
  使い回すよう修正(以前は両方ゼロ値で一致していたため検知できなかった構造自体を是正)。
  `webauthn_backend_client_test.go`にBE/BS往復のアサーションを追加。

**`bff-rails`は対象外**: Rubyの`webauthn`(cedarcode/webauthn-ruby)gemのソースを直接確認したところ、
`authenticator_data.rb`は`credential_backup_eligible?`/`credential_backed_up?`(BSに対応する
アクセサ名は`credential_backup_state?`ではなく`credential_backed_up?`。frontend-rails/without-bffへの
パスキー実装[22.9]時に実際にNoMethodErrorで発覚し訂正)というアクセサこそ持つが、登録時との一致を
検証するロジックはgem内に実装されていない。そのためbff-railsはこの不具合の影響を受けず、修正不要と判断した。

**実機での最終確認**: ユーザーの実ブラウザ(Google パスワードマネージャー同期のパスキー)で
登録→ログアウト→パスキーログインの一連の流れが完全に成功することを確認済み
(`login/finish`200、以後`/api/me`・`/api/tasks`・`/api/labels`が全て200で実データを返した)。

**既知の未対応事項: bff-railsは登録時にBE/BSフラグをbackendへ送っていない**

`bff-rails/app/controllers/passkeys_controller.rb`の`register_finish`、および
`bff-rails/app/services/backend_client.rb`の`register_passkey!`は、`credential_id`/
`public_key`/`sign_count`/`transports`/`name`のみをbackendへ渡しており、`backup_eligible`/
`backup_state`は渡していない(Rubyの`webauthn`gem自体は`authenticator_data.rb`の
`credential_backup_eligible?`/`credential_backed_up?`で登録時点でもこの値を取得できるが、
単に配線していないだけ)。
そのためbff-rails経由で登録したcredentialは、backend上で`backup_eligible=false`/
`backup_state=false`のまま保存される。

- **問題にならないケース**: 登録・ログインとも同一フレームワーク内で完結する場合
  (bff-railsで登録→bff-railsでログイン、bff(Go)で登録→bff(Go)でログイン)。
  Rubyの`webauthn`gemはBE/BS一致チェックを実装していないため、bff-rails側での
  ログインは`backup_eligible`の値に関わらず成功する。
- **問題になるケース**: bff-railsで登録したcredentialを、bff(Go)経由でログインしようとした場合のみ。
  backendに保存された`backup_eligible=false`と、クラウド同期パスキーが実際に申告する`true`が
  食い違い、bff(Go)側のgo-webauthnが本節と全く同じ`Backup Eligible flag inconsistency`で拒否する
  (逆方向、bff(Go)で登録→bff-railsでログイン、は上記の通り問題にならない)。

bffとbff-railsは`webauthn_credentials`テーブルを共有する設計(CONTRACT.md冒頭・22章)のため、
本来はbff-rails側にも同じ配線を追加すべきだが、2026-09-10時点では**クロスフレームワークの
ログイン確認をテスト計画で行った際に同エラーが再現したら対応する**方針とし、未着手のまま
既知の制約として記録する。対応する場合の変更範囲は本節の修正と同じ
(`passkeys_controller.rb`/`backend_client.rb`への配線追加のみで、backend側のスキーマ・APIは
変更不要)。

`bff-rails/`(セクション21新設)にも同じ命名規則(`/api/auth/passkey/*`)で同等機能を実装済み

backendの内部API(`/internal/v1/auth/webauthn/credentials/*`、こちらは内部API名のため
`webauthn`のままで変更していない)は共通なので、**bff(React)側で登録したパスキーが
bff-rails側のログインでもそのまま使える**(credential保存先がbackendの単一テーブルのため)

bff-railsはさらに、パスキーのみでのログイン(Keycloakのaccess_tokenが存在しない)でも
backendのTask一覧APIを呼べるよう、bffのローカルHMAC認証(`iss=bff-gin-local-hmac`)と
全く同じ形式の自前署名JWTを発行し、これをセッションのトークンとして使う(backend側の
変更は不要、共有シークレットを持つ発行者を区別しない既存の信頼境界をそのまま利用する)

### 22.9 frontend-rails/without-bffへのパスキー追加(2026-09-11、スコープ拡張)

ユーザーからの明示的な指示により、`frontend-rails/without-bff`にもパスキー(登録・ログイン)を追加した。
ログイン画面は変更せず「パスキーでログイン」ボタンを追加するのみ、登録は新設の`/account`画面で行う。

**アーキテクチャ上の判断**: `frontend-rails/without-bff`は元々(21.4)backendに一切接続しない設計
だったが、パスキーのcredential(`webauthn_credentials`)はbackendの単一テーブルに保存する設計
(22.3〜22.5)のため、backendへの接続経路が必須になる。bff/bff-railsと同じパターン
(自分のaccess_tokenでbackendのJITプロビジョニング・webauthn登録APIを直接呼ぶ)を採用するため、
Keycloakの`frontend-rails`クライアントに設定済みだった**oidc-audience-mapper(aud=backend)を
初めて活用する**ことにした(21.2、このマッパー自体は元から`realm-export.json`にあったが
CONTRACT.md上「無し」と誤って記載されたままだった。今回の調査で発覚し記載を修正した)。
これにより「backend接続無し」という設計原則はパスキー機能に限って部分的に変更されたが、
Task等のデータ取得は引き続き行わない(スコープは変わらずログイン関連のみ)。

**セッション格納方式についての注記(ユーザーからの質問への回答を反映)**: `frontend-rails/without-bff`は
Railsのデフォルトである`CookieStore`を使っており(既存の`session[:id_token]`が既にこの方式)、
今回追加する`session[:access_token]`も同様に**暗号化・署名された状態でブラウザのCookieへ格納される**。
`secret_key_base`による暗号化(AES-GCM)+署名+httponlyのためブラウザのJS(XSS含む)から生の値は
読み取れないが、bff/bff-rails(Redisにセッションを保存し、ブラウザにはopaqueなセッションIDしか
渡さない=トークン自体はサーバー側から一切出ない)より一段弱い設計である。今回新たに生じた問題では
なく、既存のid_tokenの扱いをそのまま踏襲したもの。

**JITプロビジョニングのタイミング**: `SessionsController#omniauth_callback`/`#handle_manual_callback`の
成功時に、Keycloakから取得したaccess_tokenで`BackendClient#provision!`を呼び、返ってきた`user_id`を
`session[:user]["user_id"]`へ格納する(bff-rails/AuthController#callbackと全く同じ流れ)。
`ManualOidcClient.exchange_code_for_id_token!`はaccess_tokenも一緒に返すよう戻り値を拡張した。

**パスキーのみでのログイン**: bff-rails(22.8末尾)と同じく、`Auth::LocalBackendTokenIssuer`
(`iss=bff-gin-local-hmac`の自前署名JWT、`LOCAL_AUTH_HMAC_SECRET`をbff(Go)・bff-rails・
frontend-rails/without-bffの3者で共有)を発行し、`session[:access_token]`へ格納する。
backend側の変更は不要(発行元を区別しない既存の信頼境界にそのまま乗る)。

**challengeの一時保存(begin→finish間)**: bff/bff-railsはRedisを使うが、`frontend-rails/without-bff`
にはRedisが無い(21.4、意図的に依存を持たない設計)。Redisを新たに導入するのは今回のスコープに対して
過剰と判断し、代わりに`Mutex`で保護したプロセス内`Hash`(`Auth::PasskeyChallengeStore`)で
同等の「一度きりのchallenge」(consume=読み取りと削除を1つのロック内で行う、TOCTOU対策)を実現した。
`config/puma.rb`がworkerプロセス数を指定していない(既定1プロセス)ため、プロセス内Mutexで
排他制御が成立する。複数workerプロセス構成に変えた場合はこの前提が崩れるため、その場合はRedis等の
プロセス外ストアへの切り替えが必要になる(既知の制約として明記)。

**ルーティングの命名**: bff/bff-railsは`/api/auth/passkey/*`だが、`frontend-rails/without-bff`は
元々`/api`という名前空間を持たない(`/login`・`/welcome`等が直下)ため、既存の命名規則に合わせ
`/auth/passkey/*`(`/api`無し)とした。

**CSRF**: `frontend-rails/without-bff`はActionController::Base(通常のRailsアプリ)であり、
bff-rails(ActionController::API、CSRF保護自体が存在しない)と異なりCSRF保護が有効。
新設の4エンドポイントも例外を作らず、既存の`csrf_meta_tags`(layout)からJSが`X-CSRF-Token`
ヘッダを読み取って送る標準的なRailsの方式で保護する。

`e2e/chromedp`の`TestTaskCRUD_BackendTaskLanguageRust`が、Keycloakログイン→`backend.task-language=rust`のTask CRUDで、REST・gRPC両プロトコルとも一貫して401で失敗した(admin/goのユーザー削除フローや他の全シナリオは無関係で正常)。調査の結果、backend-rust固有のバグではなく、**Keycloakのrealm設定(`bff/keycloak/realm-export.json`)側の重大な設定ミスがコア構成全体に影響していた**ことが判明した。

| 項目 | 内容 |
|---|---|
| 根本原因 | Keycloakの`sub`(subject、ユーザー識別子)クレームは、実は`basic`という組み込みclient scope配下の`oidc-sub-mapper`が担っている。`bff-gin`・`frontend-rails`・`bff-rails`の3クライアントとも`defaultClientScopes`に`basic`が入っておらず(誤って`openid`という実在しないscope名を書いていたためインポート時に黙って無視されていたと見られる)、Keycloak発行のaccess_tokenに`sub`クレームが一切含まれていなかった(id_tokenには`sub`が入るため、この非対称性で長期間気づかれなかった) |
| 隠蔽されていた理由 | Goの`encoding/json`ベースの構造体アンマーシャルは、必須フィールド(`sub`)が無くてもエラーにならず空文字列のゼロ値になるだけ(`claims.Subject=""`)。この空文字列が、JITプロビジョニング(`UserService.Provision`)経由でそのまま`user_keycloaks.keycloak_sub`列に保存され、その後の`GetByKeycloakSub("")`ルックアップでも同じ空文字列同士が偶然一致するため、**Go実装だけは表面上正常に動き続けてしまっていた**(実際には`general-user`のkeycloak_subが空文字列のまま何セッションも運用されていた)。一方Rust(`serde`)・Scala・Rails(いずれも必須フィールド欠落を厳格にエラー扱いする言語/ライブラリ)は`sub`欠落を直ちに検知して認証エラーになっており、**むしろRust側の挙動の方が正しかった** |
| 実害 | (1) `user_keycloaks.keycloak_sub`にUNIQUE制約があるため、**2人目以降の別のKeycloakユーザーが初めてログインした瞬間にUNIQUE制約違反でJITプロビジョニングが失敗し、ログインできなくなる**(今回の環境再構築後、実際に`admin-user`は一度もログインできない状態だった)。(2) 理論上、複数の異なるKeycloakユーザーが同じ空文字列のkeycloak_subを取り合うことになり、UNIQUE制約が無ければアカウント混同(なりすまし相当)にもなり得た設計上の欠陥だった |
| 修正 | `bff/keycloak/realm-export.json`の`bff-gin`・`frontend-rails`・`bff-rails`各クライアントの`defaultClientScopes`に`basic`を追加(将来の環境構築で正しくインポートされるように)。稼働中のKeycloakにも管理APIで同じ変更をその場で適用(コンテナ再起動無し)。過去に空文字列で汚染されていた`general-user`(user_id=2)の`keycloak_sub`を、実際のKeycloak sub値へ手動で修正。加えて、Go側`UserService.Provision`に空文字列の`keycloak_sub`を拒否するガードを追加(将来同じKeycloak設定ミスが再発しても、黙って空文字列のまま保存されず即座にエラーとして気づけるようにする「defense in depth」)。回帰テスト`TestUserService_Provision/keycloakSubが空文字列だと拒否される`を追加 |
| 確認 | 修正後、`TestTaskCRUD_BackendTaskLanguageRust`はREST・gRPCとも安定してPASSすることを確認。backendの全単体テスト・統合テストも修正後に再実行し全件成功を確認 |

**この発見の副産物**: この調査を通じて、`backend.task-protocol`のfeature flagがドキュメント上の既定値`rest`ではなく`grpc`のまま(過去のgRPCステータス精度検証セッションの作業残骸)DBに残っていたことも判明・修正した(既定値`rest`へ復元済み)。

## 24. backend(Go)内でのORM比較(GORM / bob、外部公開APIのページングロジック限定)

`backend/`は変更せず(新規`backend-go-bob/`ディレクトリは作らず)、
既存`backend/`の中に [bob](https://github.com/stephenafamo/bob)を使った並行実装を追加し、
Feature Flag で GORM/bob を切り替えられるようにする

### 24.1 なぜこの範囲に限定するか

対象は`/external/v1/tasks`(外部公開API)のTask一覧取得ロジックのみに限定する
(`repository.Task.ListOffsetForExternalAPI`・`ListCursorForExternalAPI`相当)

内部CRUD(bff経由)やTaskの作成・更新・削除には手を入れない

理由:
- 外部公開APIは既にセクション11で`backend.external-tasks-pagination-v2`フラグにより
  offset/cursorの2実装を切り替える仕組みが確立しており、そこへ「ORM軸」を直交させるだけで
  既存の設計パターンにそのまま乗せられる
- bobはDBスキーマからのコード生成が必要なツールであり、対象を絞ることで導入コストを抑えられる

### 24.2 Feature Flag設計(既存フラグと直交する2軸目)

```
backend.external-tasks-orm (多値、2値)
  variations: {"gorm": "gorm", "bob": "bob"}
  default_variation: "gorm"
```

既存の`backend.external-tasks-pagination-v2`(bool、offset/cursor相当)とは独立した軸として扱う
(セクション19.1・20.2で確立した「独立した軸は別flagに」という原則をそのまま踏襲)
2フラグの掛け合わせで以下の4パターンが全て到達可能になる

| pagination-v2 | orm | 実装 |
|---|---|---|
| off(offset) | gorm | 既存の`ListOffsetForExternalAPI`(変更なし) |
| off(offset) | bob | 新規、bobで同じoffsetページングを実装 |
| on(cursor) | gorm | 既存の`ListCursorForExternalAPI`(変更なし) |
| on(cursor) | bob | 新規、bobで同じcursorページング(opaqueカーソルの形式・ソート順とも既存と同一)を実装 |

レスポンスのJSON形状は4パターンとも完全に同一(内部実装の入れ替えのみ、ワイヤー契約は変わらない)。

### 24.3 実装方針

- `backend/go.mod`に`github.com/stephenafamo/bob`を追加
- bobの公式ドキュメントに従い、`tasks`/`labels`/`task_labels`テーブルからコード生成する
  - (生成先パッケージ例: `backend/internal/repository/bobgen/`)
  - 生成コマンド・設定ファイルの詳細は bob 公式ドキュメントに従うこと(バージョンにより差異があるため、実装時に最新のドキュメントを確認する)
- `repository.Task`に、GORM版と全く同じ挙動(ソート順`created_at DESC, id DESC`・keysetの絞り込み条件・total件数の扱い)のbob版メソッドを追加する
  - (例: `ListOffsetForExternalAPIBob`・`ListCursorForExternalAPIBob`、
  - または interface で抽象化して GORM実装/bob 実装を差し替え可能にする設計でもよい)
- `internal/handler/external/task.go`(または`internal/service/task_external.go`)が、
  - 既存の`backend.external-tasks-pagination-v2`に加えて`backend.external-tasks-orm`も評価し、4通りの組み合わせを解決する
- **検証方針**: GORM実装とbob実装が同じデータに対して完全に同じ結果を返すことを突き合わせテストで確認する
  - (`test/integration/task_v1_v2_compare_test.go`と同じ考え方、go-cmp での構造体比較)
