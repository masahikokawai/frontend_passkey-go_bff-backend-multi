Rails 側のパスキー実装は2つあり、そのうち frontend-rails/without-bff が「Rails アプリだけで完結させる」パターン
ただ、README には「backend の内部 API を直接呼ぶ」とも書かれているので、本当にどこまで Rails だけで完結しているのかをコードリーディングのみで確かめる

frontend-rails/without-bff(ポート :5174)が、bff(Go)も Redis も使わず、Rails アプリだけで画面・セッション・パスキーの検証まで完結させるパターン

ただし厳密には、DB(webauthn_credentials)への読み書きだけは Go の backend の内部 API 経由
Rails が MySQL に直接つなぐわけではない
このため「Rails だけで完結」と言えるのは、画面・セッション・WebAuthn の検証まで

without-bff は、React + bff とは登録できるユーザーが逆になっている点が特徴
React + bff では Keycloak ユーザーはパスキーを登録できないが、without-bff はローカルログインを持たず Keycloak
でしかログインできないので、Keycloak ユーザーが登録します(CONTRACT §22.9 でスコープを広げた

## React + bff の実装と違う点
1. challenge の保存先がメモリである(app/services/auth/passkey_challenge_store.rb)
   - Redis を使わないという方針(Cookie とメモリだけで完結させる)によるもの
   - その代わり、Puma を複数のプロセスで動かす構成や、複数のサーバーに分けた構成では、begin と finish が別のプロセスに届くと失敗する
   - Rails を再起動しても、ログインの途中だった challenge は消える
   - 今の config/puma.rb はスレッドの数(3)しか指定しておらず、プロセスは1つなので問題にはなっていない
2. sign_count の更新に失敗したときの扱いが逆
   - bff(Go)は失敗を無視してログインを成功させます(可用性を優先)
   - without-bff は update_sign_count! が例外を投げるので、ログインも失敗させます(安全性を優先)
   - 同じ機能でも方針が違うので、比べて学ぶ材料になる
3. ユーザー ID の決め方が違う
   - 登録時の JWT が Keycloak の token なので、backend は user_keycloaks を引いて user_id を決める
4. パスキーを使い回せる
   - rp_id はどのアプリでも localhost に揃えてある
     - (config/initializers/webauthn.rb)
     - WebAuthn の RP ID はポート番号を区別しないので、:5174 で登録したパスキーで、:5173(React + bff)や bff-rails からもログインできます(README 112行目)
   - webauthn_credentials テーブルを共有していて、どのアプリもログイン後に同じ形式のローカル HMAC の JWT を発行するので、成り立っている
   - ただし origin の許可は、アプリごとに自分の origin だけ
     - (WEBAUTHN_ORIGIN の既定値は http://localhost:5174)

## 注意点:未修正の既知の不具合
CONTRACT §23.2 に記録されている未修正の問題として、Keycloak でログインすると、Rails の Cookie セッションが 4KB の上限を超えて ActionDispatch::Cookies::CookieOverflow になり、ログインが完了しない

- Keycloak の access token と id token を、そのまま Cookie セッションに入れているため
- その結果、この構成でパスキーを登録する前提の「Keycloak でログインする」ところで止まってしまう
  - e2e テストでも再現しする(README 818行目)
- 修正には「Cookie だけで完結させる」という設計そのものに関わる判断が必要なので、方針が決まるまで見送られている
  - 選択肢の例:トークンを丸ごとは入れずに、必要なクレームだけ入れる/この構成だけサーバー側の保存を認める
- パスキーでのログイン(auth_mode=passkey)は、Cookie に入るのが HMAC の JWT 1つだけなので、上限を超えにくいと考えられる
  - ただし、これは実際には試していない

## 補足:bff-rails の構成
frontend-rails/with-bff は画面だけのアプリ
ログインもパスキーの処理も、bff-rails(:8102)がすべて担当する
役割分担は React + bff とまったく同じで、それを Rails で作り直したもの
「Rails だけで完結」とは逆の、BFF パターンを Rails で再現した比較用の構成
